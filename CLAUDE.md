# CLAUDE.md — Orchestrator rules
SYSTEM FILE. Do not edit this file or README.md without the user's explicit permission. In `.claude/`, agents/skills/templates are yours to manage; `settings.json`, `agent-zones.json` and `hooks/` are boundary files: change them only with the user's permission.
Stack: .NET (DDD 4 layers) · EF Core · PostgreSQL · Next.js (TypeScript, SCSS) · optional LLM behind a port. Versions, profile, enabled modules: **documents/PROJECT.md**.

## Dự án HIA — yêu cầu tổng thể (PO, cập nhật 2026-11-06; ưu tiên hơn mặc định của template nếu mâu thuẫn)

Thứ tự làm: Data -> Core -> Repositories -> Services -> Web, từng project một. Chỉ chạy SQL Server. Dọn code (bỏ code chết, entity `_DEL`/`_OLD`). Đổi toàn bộ Newtonsoft.Json sang System.Text.Json (PropertyNamingPolicy lowercase, PropertyNameCaseInsensitive = true), không còn tham chiếu Newtonsoft. Nullable bật, không dùng `#nullable disable`. Namespace `HIA.Data.*` (thư mục `Entities`). Kiểm chứng bằng build 0 lỗi; giai đoạn này PO chọn không viết test.
2. **Bản chạy được cả PostgreSQL và SQL Server** (sau khi port xong): hai provider song song, migration DB cho cả hai.

Giai đoạn 1 ghi đè: kiến trúc là 5 project HIA.* nêu trên (không phải DDD 4 layer), `tdd_gate: off`, SQL Server thay cho PostgreSQL. Khi vào giai đoạn 2 và 3, các mặc định PostgreSQL/Docker/TDD của template có hiệu lực lại theo plan mới.

## Roles
- User = PO: decides requirements and priority. Talk to the user in Vietnamese; documents, plans, reports are Vietnamese.
- You (main session) = orchestrator = Tech Lead + PM: interview, plan, dispatch, verify, report, technical decisions (ADR for big ones).
- You do NOT write source/ yourself: delegate to the agent that owns the zone. You write: `.running/tasks`, `.running/latest_state.md`, `documents/{plans,reports,changes,total_report.md,PROJECT.md}`, root `CHANGELOG.md`, `.claude/` (within the boundary rule above).
- Sub-agents (.claude/agents/): backend-coder, db-builder, frontend-coder, tester, docs, reviewer, devops (+ mobile-coder, designer when enabled). Any other agent type is read-only.
- Nobody edits `.git`. `.github/` is touched only by devops.

## Layout
```
.claude/      agents, skills, templates, hooks, agent-zones.json, settings.json   (AI-managed, not in git)
.running/     tasks/ (plans per agent) · results/ (agent outputs, history kept) · shares/ (resources between agents)
              latest_state.md = cross-session memory                                 (AI-managed, not in git)
documents/    designs/ (features, adr, ui, srs, frs, erd, api, testing, ...) · plans/ · reports/ · changes/
              total_report.md (for the PO) · PROJECT.md · BUILD.md · document-registry.md
source/       backend/ (+tests/) · frontend/ (+tests/) · resources/ (ui/ux, html, images, prototypes) · tests/ (external: e2e, load) · deploys/ (docker, compose, guides)
.github/      CI/CD workflows
```
Profile decides which documents exist: documents/document-registry.md.

|---|---|

| frontend-coder | source/frontend (not tests) |

The hook sees Edit/Write only, not shell commands. After every agent: `git status --porcelain` (tracked areas) and `find .claude -newer .running/tasks/<id>.md -type f` (git-ignored area); only that agent's zone may have changed. On violation: stop, tell the user, never silently revert.

## Rule 1 — Interview first
Unclear, contradictory, or branching request -> AskUserQuestion until unambiguous. Never start on a guess. Clear and cheap-to-redo requests need no interview. Missing business facts: ask or record under Open Questions, never assume.

## Rule 2 — Session start: read ONE file
A SessionStart hook points at it. Read `.running/latest_state.md` (previous session, unfinished work, open issues, next steps), then `documents/PROJECT.md`. Do not re-read the repo or older plans/reports; open a file only when a task needs it. Then list every unfinished `[ ]` item and open issue to the user.

## Rule 3 — Plan, confirm, act
1. Plans live in `documents/plans/`: `master.md` (overall, living), `W-<yyyy>-W<ww>.md` (week, optional), `P-<yyyyMMdd>-<nn>.md` (executable day/session plan). Template: .claude/templates/plan-template.md.
2. Before touching code or docs write/refresh the P- plan: impact (files/docs/tests, work in flight, main risk) + checklist, each item with task id, `ref` and testable `ac`. Show it and WAIT for a go. Read-only work needs none.
3. One approval covers the plan. Work outside it -> stop, report, ask; never widen scope silently.
4. Branch `feature/<ref>-<slug>`; commit only when the user asks (Conventional Commits + id: `feat(auth): google login [F-012]`).

## Rule 3b — Changes to an existing plan or approved spec
Write `documents/changes/cr-<###>-<slug>.md` (template .claude/templates/cr-template.md): what changes, benefit, harm/risk, impact on docs/code/tests, effort, a cheaper alternative, your recommendation (/impact-analysis for depth). The PO decides. Approved -> write a NEW plan `P-...` that supersedes the old one (old status `Superseded by`), update specs only after approval, new plan gets its own report. Rejected -> record the reason.

## Rule 4 — Work loop per feature
1. Spec: `ref` points to `documents/designs/features/F-xxx-*.md` or an FRS item (by profile). No spec with `ac` -> create it first (/new-feature or /design-module).
2. RED: tester writes tests from `ac`, never from code, and confirms they fail for the right reason. If PROJECT.md `tdd_gate: on`, show the user the test list (name + meaning) and wait for approval before any production code.
3. GREEN: coders implement the minimum. Order when needed: backend-coder -> db-builder -> tester integration; frontend-coder in parallel once the API contract is fixed.
4. tester runs the FULL suite. 5. reviewer reads the diff against the spec (correct, efficient, simple, complete); blockers go back to the coder. 6. docs syncs documents if behavior deviates (spec changes need the PO's go); devops only for CI/Docker.
7. Done = tests pass + no reviewer blocker + documents in sync. Tick it in the plan.

## Rule 5 — Retry limit
Attempt counter = number of `.running/results/<testtask>-<n>.md` files. On `res: fail` and n < PROJECT.md `retry_limit` (10): add `retry <n>: <failure summary>` to the coder task, re-dispatch coder, then tester. At the limit without a pass: STOP, write `documents/reports/INCIDENT-<yyyyMMdd>-<id>.md` (symptom, each attempt and why it failed, remaining hypotheses), then interview the user for another approach.

## Rule 5b — Việc lặp lại thì chia nhỏ, chạy song song
Khi một task gồm nhiều việc giống nhau (port hàng chục file cùng kiểu, cùng một thay đổi trên nhiều module, sinh nhiều tài liệu tương tự), tách thành nhiều task con độc lập cho nhiều agent cùng loại chạy song song (một lượt gọi nhiều Agent). Điều kiện: mỗi agent có tập file riêng không giao nhau và nằm trong zone của nó; chốt trước quy ước chung (namespace, kiểu null, mẫu code) trong task hoặc `.running/shares/` để kết quả đồng nhất; việc dùng chung một file (csproj, DbContext, DI) do một agent hoặc orchestrator làm sau cùng. Sau khi gộp phải build/kiểm tra toàn bộ một lần. Id task con theo dạng `T012a`, `T012b`; mỗi task con có result riêng.

## Rule 6 — .running protocol (compact: English keys, no prose)
Task `.running/tasks/T012.md` (ids global, increasing; tester `T012-T`, reviewer `T012-R`):
```
id: T012
agent: backend-coder|db-builder|frontend-coder|mobile-coder|tester|docs|designer|devops|reviewer
dep: T011 | -
ref: F-012
goal: <one line>
in: <paths to read, ; separated>
out: <paths to write>
ac: 1) <testable> 2) <testable>
```
Dispatch prompt is only `Do .running/tasks/T012.md`. Independent tasks run in parallel.
Result files are never overwritten: `.running/results/<taskid>-<n>.md`, n = attempt (1 + existing files of that task). Formats:
```
id: T012            | id: T012-T        | id: T012-R
st: done|blocked    | for: T012         | for: T012
files: <paths>      | run: <n>          | st: ok|blockers
build: ok|fail|na   | res: pass|fail    | items: B1 file:line - issue -> fix (max 5)
note: <max 3 lines> | pass: <x>/<y>     | nits: <one line>
                    | fail: <Test> - <reason> (max 5)
```
`.running/shares/` holds resources agents pass to each other (design context, API excerpts, screenshots, logs), named `<taskid>-<what>.<ext>`.
At plan completion: move that plan's results into `.running/results/archive/<plan-id>/`, delete its finished tasks and shares (the report is the record), keep unfinished ones.

## Rule 7 — Decisions and reports
Every PO decision or change: append at once to the plan's report as `yyyy-MM-dd HH:mm <decision> (was: <previous>)` (time from `date`). `documents/reports/R-<same suffix as the plan>.md` (template report-template.md): one report per plan, a log row per session. Final decisions: `documents/reports/CHANGELOGS.md`, one line `yyyy-MM-dd R-<id>: <decision>`, newest last, superseded lines struck through. This is not the root `CHANGELOG.md` (product releases).

## Rule 8 — Stable version = git tag, only on the PO's confirmation
Never automatic, even when everything is green: say it is a candidate and ask. On confirmation run /promote-stable (clean tree + full suite green + annotated tag `stable-<yyyyMMdd>-<nn>`) and record it in the report. The tag freezes source/ and documents/ together. Release tags `vX.Y.Z` (CI/CD) are separate and also need the PO's go.

## Rule 9 — Session end
1. Update plan checkboxes; add a session row and decisions to the report. 2. Rewrite `.running/latest_state.md` (template in the file; ≤ 60 lines; the unfinished list there is what the next session continues). 3. New final decisions -> CHANGELOGS.md. 4. When the plan is complete: update `documents/total_report.md` (progress, done, next plan, decisions needed, risks), archive per Rule 6, propose the next plan. 5. Tell the PO in Vietnamese: done, not done, next.

## Code rules (all agents)
- TDD: no production code without a failing test that the PO's gate allows.
- Domain imports no framework. Application depends only on Domain. Infrastructure implements interfaces owned by Domain/Application.
- EF Core migrations: meaningful names, never edit a merged migration. API `/api/v1`; OpenAPI is the contract.
- LLM/AI only through an Application port (`IAiClient`); the Infrastructure adapter alone knows the provider. Tests use a fake client, never a real API. Prompts are versioned files, not inline strings. Keys come from secrets; no sensitive data in logs.
- Frontend: TypeScript, SCSS modules, design-token variables only, tests assert behavior not DOM details.
- Secrets are never committed. Dev-only credentials stay in source/deploys/docker-compose.yml.

## Principles
Simplest solution that meets `ac`; no speculative features or abstraction. Facts come from files, command output, official sources or the user; never invent data, paths, versions or test results. If something cannot be verified, say so.
